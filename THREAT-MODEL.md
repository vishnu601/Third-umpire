# Threat model

Third Umpire: a self-hosted hackathon submission and judging portal (Django, SQLite, one container). This is the
written defence against Sybil accounts, ballot stuffing, collusion, and the ordinary web attacks around them, for
the DOGFOOD 2026 "Threat Model" bonus.

**How to read it.** Every defence below points at the function that implements it and at the test that proves it.
`tests/x.py::name` is a committed test (the suite is green: 228 passed). `probe` means "checked once by hand
against the test client, not a committed test", and each of those is listed again in section 4 as a test we owe.
`verify.sh` means a curl probe in `scripts/verify.sh`. Where a defence does not exist, or only half exists, we say
so in the table's last column and in section 4. Community voting and comments (T3) have their own section, 3.

## 1. Scope, assets, actors, trust boundaries

### Assets

| Asset | Why it matters | Where it lives |
|---|---|---|
| Scores (`Review`, `CriterionScore`) | They decide the prizes. Peer scores must stay private while judging runs. | SQLite |
| Rankings and rank bands | The published result; derived from scores plus rubric weights (`services.event_results`). | Computed, cached in `/data/cache` |
| Submissions (`Project`, images, answers) | Integrity and the deadline. Drafts are private. | SQLite, `/data/media` |
| Accounts and sessions | Impersonating a judge or organizer is the shortest path to any of the above. | SQLite (`auth_user`, `django_session`) |
| Audit log (`AuditLog`) | The organizer's evidence that nothing changed silently. | SQLite |
| Invite tokens (team join links, judge invites) | A bearer credential for a role. | SQLite; 144-bit `secrets.token_urlsafe(18)` (`models.mint_token`) |

### Actors

| Actor | What they can legitimately do | Modelled as |
|---|---|---|
| Visitor | Gallery, event pages, published results | No session |
| Participant | Own team, own project until the deadline | `EventRole.participant` + `TeamMembership` |
| Judge | Read and write their own reviews on assigned projects | `EventRole.judge` per event |
| Organizer | Configure the event, assign, read every review, publish, export | `EventRole.organizer` per event |
| Admin | Same as organizer on every event, and may create events | `is_superuser` (there is no Django admin site installed) |
| Outside attacker | Anything reachable without credentials, or with a self-made account | Open signup, no email verification |
| Malicious insider (judge) | A real judge who inflates, deflates, coasts, or coordinates | Section 2, T10 to T13 |
| Malicious insider (organizer, admin) | Has write access to the rubric, assignments, withdrawals, publication | Section 2, T14; admins are trusted (section 4) |

### Trust boundaries

```
 browser ──HTTPS──▶ reverse proxy (operator's; NOT shipped) ──HTTP──▶ gunicorn ▶ Django ▶ SQLite + /data volume
   1                        2                                     3            4              5
```

1. **Browser to proxy.** Untrusted input. TLS is the operator's job. `docker-compose.yml` publishes only
   `127.0.0.1:8080`, so nothing is exposed until someone puts a proxy in front on purpose. With `DJANGO_HTTPS=1`
   the app sets secure cookies, HSTS and trusts `X-Forwarded-Proto` (`config/settings.py`).
2. **Proxy to gunicorn.** `X-Forwarded-For` is ignored unless `DJANGO_PROXY_COUNT` says how many proxies we run
   (`ratelimit.client_ip`). The proxy is trusted to overwrite that header.
3. **Django to services.** Every view (`pages.py`, `views.py`) calls `services.py`, which holds the rules and does
   the role checks. Templates hide nothing that the service layer does not also refuse.
4. **App to SQLite and the media volume.** Anyone who can read or write `/data` bypasses every control here:
   the DB, the uploads, and the file-based cache (which holds the rate-limit counters and pickled results) are one
   trust zone. The container runs as uid 10001 (`Dockerfile`).
5. **Shell on the host or container** (`manage.py seed --fixtures`, `sqlite3`). Fully trusted, and unaudited (T14).

### Judging integrity: biased, lazy, colluding and stuffing judges

| # | Threat | Attack | Defence in the code | Evidence | Residual risk |
|---|---|---|---|---|---|
| T10 | Ballot stuffing by a judge | Score one project many times, score projects nobody assigned, score after judging closed or after results went out | One review per judge per project: `Review` has `one_review_per_judge_project`, and re-submitting replaces it (`services.save_review`). Only assigned projects (`not_assigned` 403), only submitted, non-withdrawn ones, only before `judging_close`, and never while results are published (`results_published` 403: scores are frozen; an organizer must unpublish first, and that is audited). Scores must be integers 1 to 5 for every criterion, and the DB has a check constraint (`score_on_five_point_scale`). Assignment is controlled by the organizer, so a judge cannot choose whom to score (no cherry-picking). | `tests/test_t2_pages.py::test_judges_cannot_score_what_is_not_theirs`, `::test_scores_out_of_range_are_rejected`, `::test_judging_closes`, `tests/test_hardening.py::test_scores_are_frozen_once_results_are_published`, `tests/test_product.py::test_withdrawn_projects_cannot_be_assigned_or_scored` | Real judges can still score 5 across the board within the rules. That is a "biased judge", T11. Organizer unpublish then judge edit then republish is possible, and every step is in the audit log, but nothing forbids it. |
| T11 | A biased, lenient or harsh judge; a project reviewed by an unlucky draw | A judge who gives everyone 5, or everyone 2; a project that only met harsh judges | The ranking is not a plain average. It fits `score = project quality + judge leniency + noise` by alternating least squares with shrinkage, so a uniformly lenient or harsh judge's offset is estimated and removed (`scoring.fit`, `services.event_results`); the results page shows rank bands and "too close to call" from a residual bootstrap; the public never sees per-judge leniency (`pages.py:results`). Full method and proof: `JUDGING.md`, `docs/proof/`. | `tests/test_scoring.py::test_harsh_judge_on_a_strong_batch_is_not_mistaken_for_a_weak_batch`, `::test_shift_of_one_judge_does_not_change_the_ranking`, `::test_shrinkage_pulls_low_evidence_judges_towards_average`, `::test_recovers_an_exact_additive_design`, `::test_near_tie_is_flagged_as_too_close_to_call`, `tests/test_simulation.py::test_model_beats_mean_and_zscore_when_tracks_differ_in_quality`, `tests/test_results.py::test_results_recompute_when_a_score_changes` | The model removes a judge's *constant* offset. | T12 | Collusion: two judges, or a judge and a team, agree to inflate a project | Two judges both give a friend's project 5/5/5 and lower its rivals | Judges cannot see each other's scores in the portal, so they cannot coordinate through it (T01). Assignment is the organizer's (auto-assign is deterministic and least-loaded; batch assignment is audited: `assignments.batch`, `assignments.generated`), so a judge cannot pull a friend's project into their queue. Conflicts of interest are excluded (T07). `reviews_per_project` (default 3) and `tiebreak_suggestions` add independent reviewers where the result is contested. What we rely on is: independent reviewers (default 3), wide bands that flag close calls, and an organizer who reads `project_reviews` and the audit. Coordination outside the portal cannot be prevented. See the next steps in section 4. |
| T13 | A lazy or flat judge, unfinished review batches | A judge gives every project 4/4/4, or does 3 of 20 reviews | `scoring.flat_judges`: three or more reviews with identical criterion scores on every sheet are left out of the fit (they say nothing about which project is better), are still counted and flagged, and do not count as a bridge when checking that every project can be compared. Unfinished work: `integrity_report` flags `light_judges` (a third or less of the median review count), `under_reviewed` projects and pending assignments, and the manage page warns before publishing with reviews outstanding. The fixture's planted cases are found: flat jdg_07, light jdg_01 and jdg_23, 8 projects at 2 reviews, duplicate prj_07 and prj_41. | `tests/test_scoring.py::test_flat_judge_is_excluded_from_the_fit_but_counted`, `::test_a_flat_judge_does_not_count_as_a_bridge`, `::test_two_equal_reviews_are_not_enough_to_call_a_judge_flat`, `::test_same_mean_from_different_criterion_scores_is_not_flat`, `::test_project_seen_only_by_a_flat_judge_still_gets_a_score`, `tests/test_t2_pages.py::test_integrity_report_finds_the_planted_cases`, `::test_dashboard_shows_the_planted_cases`, `::test_top_up_assigns_judges_to_under_reviewed_projects`, `tests/test_product.py::test_publish_warns_when_reviews_are_pending` | The flat rule is exact equality on all criteria, so a judge who varies one score by a point now and then evades it. A judge who scores at random (noise, not a pattern) is not detected: the model treats it as noise and the bands widen. Nothing stops an organizer from publishing with reviews outstanding (it is a warning). |
| T14 | An organizer or admin manipulates the result | Change weights after seeing scores, withdraw a rival, reassign judges, unpublish and re-publish, add a friendly co-organizer, edit a review directly | The app has **no endpoint that lets an organizer create or change a judge's review**; `save_review` requires the judge's own login and assignment. New criteria are locked once reviews exist (`add_criterion`: `rubric_locked`). Every organizer lever writes an audit entry with before/after where it matters: `rubric.weights_changed`, `project.withdrawn` (with reason), `assignments.*`, `results.published` / `unpublished`, `role.granted`, `event.updated`. The audit page and `audit.csv` are organizer-only; the log has no edit or delete route in the app. Exports are downloaded, so a copy can be kept off the server. | `tests/test_t1_pages.py::test_rubric_is_locked_once_reviews_exist`, `tests/test_product.py::test_organizer_adds_a_co_organizer_by_email` (asserts `role.granted`), `::test_organizer_withdraws_a_duplicate_and_it_leaves_results_and_gallery` (asserts `project.withdrawn`), `tests/test_t2_pages.py::test_stage_csv_exports` (audit CSV) | **The audit log is append-only by convention, not by mechanism.** `AuditLog` is an ordinary table: anyone with database access (an admin with a shell, a host operator, a leaked volume) can edit or delete rows and the reviews they describe, and nothing would show it (no hash chain, no external anchor). ### Credentials, abuse of the front door, configuration

| # | Threat | Attack | Defence in the code | Evidence | Residual risk |
|---|---|---|---|---|---|
| T15 | Credential stuffing and brute force | Many passwords against one account; many accounts from one address | `pages.py:login_view` calls `ratelimit.hit` before authenticating: 10 attempts per account per 15 minutes, 50 per address per 15 minutes; a locked account refuses even the right password. Signup: 30 per address per hour (`DOGFOOD_RATE_LIMITS_SIGNUP_PER_IP`). Passwords: Django's PBKDF2, minimum 10 characters and not in the common-password list (`AUTH_PASSWORD_VALIDATORS`, checked in `SignupForm`). Login and the rate-limit key are case-insensitive on email (`EmailAuthenticationForm`), so `A@x` and `a@x` share one counter. No MFA, no breached-password check, no password reset or change page (no email). Signup says "an account with this email already exists", which lets anyone test whether an email is registered. ### Threats considered and deliberately not covered here

- **Denial of service at the network layer**: the reverse proxy's job.
- **Supply chain**: three runtime dependencies (Django, gunicorn, Pillow), pinned in `requirements.txt`; we do not
  run an automated vulnerability scan in CI.
- **Timing side channels, browser bugs, physical access.**

## 4. Known gaps and what we would do next

Honest list. Nothing here is hidden behind a claim above.

**Gaps that exist today**

1. **No email verification, no password reset, no MFA.** The portal must run offline, so it sends no email. Signup
   is open, so a Sybil account is cheap, and a judge invite's "email must match" check (`accept_judge_invite`) is a
   guard against mistakes, not authentication: the single-use, 144-bit token is the real credential, and it should
   be handed over over a private channel. A forgotten password needs an organizer with shell access.
2. **The audit log is not tamper-evident.** It is written by the app and never edited by it, but a database
   administrator can change or delete rows undetected. Deleting an `Event` cascades to its audit rows.
3. **Admins (`is_superuser`) and organizers are fully trusted.** They cannot compete in their own event, write
   reviews or vote, but they can change the rubric, assignments and settings. The defence is the audit trail, not
   prevention.
4. **Colluding or project-specific biased judges are not detected**, only diluted (independent reviewers, bands,
   tie-break reviewers, organizer reading `project_reviews`). The flat-judge rule is exact equality.
5. **Rate limiter is best-effort**: a non-atomic counter in a file cache shared by the gunicorn workers, and the
   per-account limit allows targeted lock-outs. Login, signup, votes and comments are limited; team creation, uploads and score posts are not.
6. **SQLite is a single writer** and the results analysis is recomputed whenever a score or weight changes; a
   flood of writes from one authenticated user is not throttled.
7. **No CSP on HTML pages** (only on `/media/`), and secure cookies are opt-in via `DJANGO_HTTPS`.
8. **Deadline check is not atomic with the write** (sub-second window), and one project per team is a service
   check, not a DB constraint.
9. **Audit gaps**: comment-only review edits, exports, failed logins, and shell-side imports are not recorded.
10. **No global upload quota**, and image metadata is not stripped.

**Tests we used to owe, now committed** in `tests/test_threats.py`: CSRF on HTML forms and the API's refusal of
form and text bodies (T03), `/login?next=` (T17), hostile text escaped on six pages (T09), the `save_review` and
`join_team` conflict branches and organizers not competing (T07), media path traversal (T10), and secure cookies
and HSTS under `DJANGO_HTTPS=1` (T04).

**Tests we still owe**: a forged `submitted_at` in a request body (T05; the code path never reads one), and the
`IntegrityError` race branch of `create_team` / `join_team` under real concurrency (T06).

**What we would do next, in order**

1. **Judge x project outlier flagging.** The fitted model already has a residual for every review. Flag a review
   whose residual is beyond about 2.5 standard deviations, and any judge whose residuals are all positive on one
   team's projects, in `integrity_report`. That is the cheapest real collusion signal. Add a robust (trimmed or
   Huber) fit as an option.
2. **Hash-chain the audit log** (each row stores the hash of the previous row and its own content), print the head
   hash on the audit page and in `audit.csv`, and tell organizers to note it at publication. Optionally forbid
   `UPDATE` and `DELETE` on the table with a SQLite trigger.
3. **Organizer sign-off flow**: make "publish" require a second organizer, and freeze the rubric weights at the
   first review, not only new criteria.
4. **Rate-limit more doors** (team creation, uploads, score posts per judge) and make the counter atomic
   (`cache.add` plus `incr`, or a small SQLite table).
5. **Opt-in verification** for deployments that do have mail: email confirmation at signup, password reset, and
   optional TOTP for organizers and judges.
6. **Strict CSP on HTML pages** after moving the dashboard's inline script to a served file. Make demo mode
   opt-in: ship the production compose file with it off and the demo as a separate override file.
7. **Per-event participant caps** and a "possible same person" flag (same
   IP at signup, same email domain and name) for organizers to review.
